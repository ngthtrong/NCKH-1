\FormSection{3. Novelty and innovation:}
\FormResultText{The project integrates key multi-tenancy mechanisms into a practical Kanban application and evaluates them together in a deployed prototype. The Level 3 Pool architecture allows multiple tenants to share the application and database while maintaining tenant-specific identity context and data protection. Each tenant can also customize branding, work-in-progress (WIP) rules, and extended data fields at runtime without changing the database table structure.}{The project integrates key multi-tenancy mechanisms into a practical Kanban application and evaluates them together in a deployed prototype. The Level 3 Pool architecture allows multiple tenants to share the application and database while enforcing tenant-specific identity context and row-level data security. The application also supports runtime customization of branding, workflow rules, and extended data fields.}
\FormSection{4. Research results:}
\FormResultText{The project designed, developed, and deployed the TenantFlow web application as a software service. It supports multiple organizations sharing infrastructure while maintaining separate workspaces and configurable Kanban workflows. In testing, all 1,500 alternating tenant requests retained the correct context, and 600 database fault-injection cases recorded no cross-tenant data leaks. Under an 80-virtual-user workload, p95 latency for four regular tenant groups was approximately 242--277 ms, below the 500 ms target. The system also demonstrated rate limiting, WIP rule enforcement, and support for extended data fields. The p99 latency remained approximately 1.99--2.45 seconds in the single-server test environment and requires further optimization.}{The project developed and deployed the TenantFlow prototype using React, Spring Boot, PostgreSQL, Redis, and Caddy on AWS EC2. Tests recorded consistent tenant context in all 1,500 alternating requests and no cross-tenant data leaks across 600 database fault-injection cases. Under an 80-virtual-user workload, p95 latency for four regular tenant groups ranged from 242 to 277 ms, below the 500 ms target. Rate limiting rejected 92.66\% of the aggressor tenant's over-limit requests. Runtime customization and extended-field tests also succeeded. The p99 latency remained approximately 1.99--2.45 seconds in the single-node test environment and requires further optimization.}
